\subsection{Recurring Sprint Items}

\subsubsection{Product Backlog}
Features will be added to the product backlog in consultation with the project owner and the System Requirements Specification. Changes proposed by stakeholders will ultimately by voted upon by the development team before adoption. The product backlog will be tracked by the project Jira board.

\subsubsection{Sprint Planning}
There will be a total of eight sprits across both semesters, with one elapsed from the first revision of this document. Planning for the next sprint will occur in discussion with the project owner during the end of the previous sprint.

\subsubsection{Sprint Goal}
During the sprint review stakeholder consultation the development team shall ellicit a sprint goal from the product owner. Failing a clear directive from the owner, the team shall identify necessary technical debt to remove to improve reliability.

\subsubsection{Sprint Backlog}
After the determination of the sprint goal, the group shall discuss which features most directly accomplish the goal and are achievable within the available timeframe. The sprint backlog will be tracked in a Jira scrum board alongside the product backlog.

\subsubsection{Sprint Retrospective}
The sprint retrospective will occur during the creation of the sprint review slides. Reporting will take the form of the provided template, documenting (among other things) the: goal, completed items, and burndown chart. Individual sprint reviews are to be completed by team members on their own time frame, before the due date.

\subsubsection{Individual Status Reports}
Individuals of the group will submit a report that can be broken down into the following 6 sections:
\begin{enumerate}
    \item \textbf{Sprint Goal}: This will outline the goal of the completed sprint within a sentence or two.
    \item \textbf{Sprint Backlog}: This is a table of tasks assigned to the team to finish within the sprint. It will contain the name of the task, the expected time to finish and the actual time to finish.
    \item \textbf{Individual Time Expenditures}: This will include a table of the tasks assigned to the individual how much time was put into the each task, and approximate percentage they think the task is finished.
    \item \textbf{Burndown Chart}: This will be an image of line graph which displays the expected remaining hours over the days of the sprint and the actual hours remaining over the sprint.
    \item \textbf{Individual Retrospective}: This will include 3 sections with three distinct bullet points in each section for the individual to fill out. These three sections are what actions/items they will start working on, will stop working on, and continue to work on.
    \item \textbf{Peer Review}: This will be a table evaluating the other team members based on the five criteria: Participation, Communication, Professionalism, Work quality, and Overall performance.  They will be rated on the scale of 1-5 where 1 is abysmal and 5 is perfect
\end{enumerate}

\subsection{Closeout Materials}

\subsubsection{System Prototype}
The final prototype for the system will include a usable website that anyone can interact with in order to find what piece of equipment or tool they are looking for. Additionally, there will be a server that will be hosting the website on the local network of the SD labs (AKA SkyNet) and a kiosk available to students at the door of Steven's office in ERB 208 that students can interact with.
We will present this by showing Steven the capabilities of the website through demos and interacting with the system such that he is satisfied with the prototype.


\subsubsection{Project Poster}
The poster will include 5 sections:
\begin{enumerate}
    \item \textbf{Background}: Which will include the purpose and why we are making the product
    \item \textbf{Key Requirements}: Includes the high-level requirements, and their descriptions, of our project
    \item \textbf{Implementation and Test Plan}: This will be broken down into the major sections of the project (e.g. frontend and backend), how we designed them (e.g. what framework was used and why), and how we plan to test.
    \item \textbf{Conclusion and Future Work}: Mainly detailing if our goals were accomplished and what we would like to work on in the future if we could.
    \item \textbf{References}: list of places of information that helped us accomplish the final prototype.
\end{enumerate}

\subsubsection{Web Page}
The project web page will include all project requirements as it will be the medium for interacting with our target audience. More specifically, this will hold equipment positions (with visuals), A ticket system to inform Steven McDermott of equipment needs or damaged equipment, and finally a way to allow admins to modify what equipment is held in the labs. The website will be made available to the public but can only be accessed through the local network of SkyNet. Initial prototypes of the website will be made available by December 2026 and a finalized website will be available around May 2027. Continuously being updated as we make progress throughout the sprints.

\subsubsection{Demo Video}
In our demo video we will try to emphasize our major features of the website including visualizations, the ticket process, and admin privileges for Steven to use. The video should be approximately 2-5 minutes depending on how much of the requirements we will be able to finish within the time frame. 

\subsubsection{Source Code}
Source code will be made available through github where we will be able to maintain and implement a version control system. The source code will not be directly provided to the customer as they are only interested in the usability of the website rather than interacting with the code. Alternatively, they will have access to the code through the public github repo we will use and the code on the local server hosting the website. With this being a public website, a license will be needed to ensure ownership is sustained which has been chosen to be the MIT license. This license will be visible within the github repo and in the main directory of the source code.

\subsubsection{Source Code Documentation}
Because we will be using ReactJS and PostgreSQL for our project, there are not any automatic documentation programs to use. Instead we will create documentation manually using markdown files that will allow for easy to read documentation while also being flexible in how we change the documentation. At a high level, this documentation will include the polymorphic hierarchies we create, function descriptions (including expected parameters and outputs), and instructions on how to setup the website. This will also include examples for easier understanding.

\subsubsection{Hardware Schematics}
The kiosk is thus far the only planned piece of hardware we will be using and therefore no hardware schematics will be used. 

\subsubsection{CAD files}
The kiosk for the project will be need to mounted, however, it has not been finalized whether it is better to use a store bought mount or use a 3D printed mount. If it were decided to 3D print a mount, PLA or a PETG filament will be used and the software to convert to binary files for the 3D printer to read would be CURA. 

\subsubsection{Installation Scripts}
Installation instructions will be provided as both a pdf and a markdown files for easy readability. These will include commands to build the website and the necessary environmental variables needed to run the program. Because we are using docker, there will be a few package installation scripts necessary for the frontend and backend, however, with docker there will only be a centralized build script for the user to run. 

\subsubsection{User Manual}
The customer will be provided with a manual of how to install required packages and build the website, additionally, they will be given a demo video on how to use the website.
